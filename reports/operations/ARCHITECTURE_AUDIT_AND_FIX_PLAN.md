# Architecture audit and proposed final-change plan

Audit: 2026-11-18 UTC (November 17 Pacific). This is a finding and planning document, not a deployment approval or a claim that fixes have been made. The application, live configuration, schedules and original 48-hour evidence were not changed. Only audit artifacts and DEV_LOG were written.

No finite review can establish that every possible bug has been found. This review covers the principal application boundaries, existing regression suites, live configuration and scheduled-run receipts. Provider outage injection, production load tests, live mutation tests and destructive recovery tests were deliberately not run during the read-only audit. Source findings must be tested against the final candidate before closure.

## Architecture and the central problem

Telegram and the HTTPS dashboard enter OpenClaw. Main has the private assistant workspace and local Gemma; Researcher has an isolated public workspace. Router hooks classify privacy/complexity, check the local endpoint and select a platform model. Restricted tools retrieve data. Authenticated Telegram commands authorize email approval, task changes and trusted memory. Native automation scripts generate reports and Telegram notifications. Application SQLite lives on local disk, with separate immutable application snapshots and an encrypted native-state archive in GCS. Tailscale links Cloud Run Instance to laptop Ollama and supplies dashboard identity.

The main architectural weakness is inconsistent request handling across channels and agents. Telegram has special fresh-session dispatch for narrowly recognized requests. Dashboard requests do not use that dispatch. Reports have fixed parameters, while the user can ask arbitrary questions. Tool selection does not always account for the chosen model's tool restrictions. Passing the prepared demo therefore did not establish ordinary conversational behavior.

## Proposed fixes and acceptance criteria

Labels: **Confirmed** means directly observed or structurally demonstrated in source/offline reproduction. **Risk** means a plausible failure requiring targeted reproduction. **Limit** means deliberately constrained behavior to disclose, not automatically a requirement to expand scope. P0 denotes a privacy/correctness gate; P1 denotes significant functionality/reliability; P2 denotes clarity, maintenance or further hardening.

## What must remain protected

Do not loosen privacy to make cloud demos pass. Do not expose Telegram approval authority to models, webpages or shared dashboard visitors. Do not change dedicated account restrictions, turn the calendar writable, silently resend uncertain mail, reset completed outbox records, erase taint/history or replace failed evidence. Historical48h logs remain immutable.

## One-candidate execution plan — not started

1. Agree final supported behavior and must-fix set, prioritizing R01/R05/S01/S06 and A01–A04/D01/R07/R08. Resolve uncertain items with isolated reproductions before changing code. Not every P2 item requires implementation; documented limits are legitimate.
2. Build one coherent request/dispatch contract across Telegram and dashboard: public weather/search, constrained private read intent, authenticated mutations. Preserve sender/date/query context and use capability-aware routing.
3. Fix routing/failure handling and monitoring together. Reproduce historical suffix/taint defect, prove actual models, explicitly bind recurring probes and distinguish simulation from real provider recovery.
4. Address provider pagination/time budgets/report scoping, email review UX, recap labeling and alert delivery reconciliation. Add targeted regression tests based on the above counterexamples, not merely more happy-path tests.
5. Fix demonstrated durability/startup issues, review native memory authority and security findings. Verify snapshots/restore in an isolated environment; no live data resets.
6. Run pinned-runtime root/plugin checks and an isolated acceptance matrix. A passing unit suite alone is not the go-live gate.
7. Only after authorization, deploy the one candidate with source/image/config manifest and rollback plan. Verify actual startup, credentials, both models, provider reads, all four skills, delivery receipts, approval/duplicate safety, grader access and restart behavior before freezing it.
8. Under the user's chosen rule, start a NEW48-hour window only after final deployment validation and freeze. No new window was started in this audit. Compute `readiness time + 48h` against the exact November19 submission deadline; any later fix/redeploy requires revisiting the schedule. Do not promise a full48h if insufficient wall time remains.
9. During that window, verify expected versus served models, every scheduled job, timestamp coverage, delivered messages, persistence checkpoints and incidents. Preserve original and new windows as separate evidence. Package truthful final reports afterward.

## Mandatory pre-freeze acceptance matrix

- Both channels, Main and Researcher: clean and reused sessions; arithmetic, several reasoning phrasings, public search paraphrases, current weather versus forecast, sender/date mail, calendar tomorrow, task reads and capability questions.
- Routing: local healthy, local missing, listed-but-stalled, recovery, both unavailable, public cloud with laptop off from boot, private held, actual/injected429 distinction, OAuth revoked, mixed private/public follow-up, attachments and persistent taint.
- Proactive: briefing with weather and unread mail, recap with correct dates/activity, nonempty alert, empty suppression, failed/unknown delivery, deduplication, scheduled local/cloud probe and credentials after restart.
- Provider data: empty, >page-size, partial, stale, malformed, timeouts, multiple messages/read flags, HTML/MIME hostile content, DST/all-day/overlap/description-only project context.
- Mutations: authenticated Telegram success, unauthorized dashboard/model denial, invalid/expired/mismatched approval, duplicate add/complete/send, ambiguous delivery, checkpoint failure and restore. Actual email sending requires explicit human approval.
- Durability/security: concurrent writes/checkpoints, old/new snapshot ordering, corrupt/missing archive, startup interruption, no credential output, no unauthorized external effects, trusted-memory integrity, grader invitation reuse and scope.

Every case needs expected result, actual receipt, model/tool identity, route, timing and side-effect checks where applicable. A failure remains open or is explicitly accepted as a documented scope limit. No further blanket “everything ready” claim should be made from a rehearsed path.
